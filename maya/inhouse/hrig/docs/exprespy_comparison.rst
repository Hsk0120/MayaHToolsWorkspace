exprespy・Bifrost・C++の評価比較
========================================

2026年10月9日、Maya 2027で、負荷ごとに同じプロセスで標準DG・C++・Bifrost・exprespyを比較しました。
単一入力の行列追従と、実LimbRigのSoft IK部分が対象です。
exprespyは研究用の構築時差し替えで、hrigの正式なバックエンドではありません。

行列追従は初回実行の24条件・168反復、LimbRigはSoft IK修正後の別実行の12条件・84反復です。
掲載する36条件・252反復は2実行を組み合わせています。LimbRigの修正後実行は同日22:59（JST）に開始しました。
各負荷内の4実装を比較し、負荷間の時間を直接比べません。Soft IKの修正は行列追従の構成を変更しません。
全36条件で出力の長さ・有限値・実モード一致、Cached Playback無効、EM fallbackなしを確認しました。
修正前のLimbRigの速度は、このページの比較に使用していません。

測定環境と方法
----------------------------------------

Maya 2027／API 20270000、Windows 11（10.0.26200）、Python 3.13.9、
Intel Core i7-12700KF、論理CPU20、Mayaスレッド設定20です。

.. list-table:: ロードしたプラグイン
   :header-rows: 1

   * - プラグイン
     - バージョン
   * - exprespy
     - 3.0.1.20260417
   * - hrigNodes
     - 0.1.0
   * - bifrostGraph
     - 3.0.0.0-202602040323-9df3db7

同じ入力アニメーションを使用し、各条件で120フレームをウォームアップした後、
240フレーム×7回を測定しました。ケースと評価モードの順番は固定seed 20261009で並べ替えています。
構築・ロード・コード設定・初回コンパイル・出力の読み取りは反復時間の外です。
構築時間は計測経路の違いを含むため、構築速度の比較には使用していません。

測定値は ``currentTime(update=True)`` と全出力への ``dgeval`` を含む経過時間です。
PythonからMayaへの呼び出し、入力アニメーション、Transform、IK等の評価も含みます。
描画・スキニング・UIは含まず、ビューポートFPSや計算ノード単体のcompute時間ではありません。
SerialはEM評価グラフの直列評価で、Bifrost内部を含むCPU 1スレッド固定ではありません。

他プロセスのCPU負荷も参考値として記録しました。行列追従168反復の概算は中央値1.613core、最大3.655core、
修正後のLimbRig84反復は中央値1.170core、最大3.400coreでした。
Windows全体のCPU秒から当該プロセスのCPU秒を引き、経過秒で割った概算で、
取得区間やOSの粒度による誤差を含みます。評価時間から差し引いて補正していません。
過去の計測値へ今回の値を足して比較せず、同じ実行内の条件を比べています。

行列追従300個
----------------------------------------

標準構成は ``multMatrix -> offsetParentMatrix`` です。C++・Bifrost・exprespyも
``offset * sourceWorld * parentInverse`` の倍精度行列を同じ専用Transformへ渡します。
各方式とも1対象につき1計算ノード、Bifrostは1対象につき1graphShapeとその親Transformです。
配列を1グラフへまとめる方式は測定していません。

独立した300出力と300段の階層を分けました。全300出力を6時刻で標準DGと照合し、
全24条件で最大行列要素差0でした。許容値は1e-6です。
300段は長い依存経路のストレス試験で、通常の腕・脚全体の高速化率を示しません。
入力は移動・回転のみで、parentConstraintの複数入力・軸スキップ・jointOrient等の完全互換比較ではありません。

実LimbRig30個のSoft IK
----------------------------------------

実際の ``LimbRig`` を30個作り、IK／全機能LOD、各4出力関節で評価しました。
Soft IK部分だけを差し替え、既存IK solver・拘束・その他のリグノードは同じ構成です。
修正後の標準Soft IKは ``divide``・``subtract``・``sum``・``multiply``・``power`` と
``condition`` の標準DGノードで、
C++・Bifrost・exprespyもSoft IKの倍率を計算する構成です。
距離とsoftnessを同じキーで動かし、Soft IKが効く領域も通過させます。
これはhrig全機能のexprespy化や、キャラクター全体の速度比較ではありません。

修正後の4実装を同じプロセスで測り直しました。全120出力を6時刻で修正後の標準DGと照合し、
12条件の最大行列要素差は2.3981e-6でした。許容値は0.003です。

実装の制限と解釈
----------------------------------------

exprespyは `upstreamソース <https://github.com/ryusas/maya_exprespy>`_ で
``kGloballySerial`` を指定し、Pythonコード実行ではGILを取得します。
Parallelでもexprespyノード同士の並列実行を示しません。hrigのC++ノードは ``kParallel`` です。
入力やTransform等の並列化を含む構成全体の評価時間として解釈してください。

研究用のexprespy差し替えは構築後に解除しても、生成済みノードのDG評価を維持します。
保存メタデータの ``hrigBackend`` は ``standard`` のままで、実ノード型を計測結果へ記録しています。
正式バックエンドの追加、任意リグの自動変換、Undo/Redo・保存再読み込みの比較を保証するものではありません。
Bifrostの構築制限は :doc:`constraint_performance` を参照してください。

Soft IKの微小距離の修正
----------------------------------------

Maya 2025・2027で、標準 ``multiplyDivide`` は分子と分母が等しくても、
約1e-5以下の微小入力の除算で出力100000を返すことを確認しました。
標準Soft IKの距離1e-6で見られた倍率100000は、この除算の挙動によるもので、
入力の微小な丸めだけでは説明できません。

新規生成する標準Soft IKをdoubleの ``divide``・``subtract``・``sum``・``multiply``・``power`` と
``condition`` に変更しました。既存の汎用ScalarGraphやC++・Bifrostの式は変更しません。
Maya 2025・2027で各148件の機能検証が成功しました。新しいSoft IKの5件と原点近傍の2件も
この合計に含まれます。詳細は :doc:`test_results` を参照してください。

微小距離1e-8・1e-6の倍率増幅を解消し、1e-12も有限性と上限を適用した参照値に一致することを確認しました。
cm/m/mmでの入力・評価、生成変換ノードの所有、作成と値編集のUndo/Redoも検証しています。
Maya 2025で保存した新しい修正済みグラフをMaya 2027で開き、同じ54入力のratio差0と単位の維持を確認しました。
LimbRigの性能値は、修正後の再計測結果を使用します。

修正後の微小距離の実リグ追加照合では、4実装×15入力の60組合せを収集し、全3,397数値が有限でした。
標準の15入力のratioは0〜1、参照との差は最大4.9516e-8、IK handleの参照位置との差は最大2.9803e-10cmでした。
倍率増幅の修正を確認していますが、RP solverの終端残差は最大約0.0100000182cmで、下記の制限が残ります。

修正は新しく生成するグラフへ反映します。保存済みの旧DGグラフは自動移行しないため、
新しいhrigを読み込み、リグを再構築してください。すでに標準バックエンドの場合の
``set_backend("standard")`` は何も変更せず、旧グラフの更新にはなりません。

既存の境界仕様も残ります。全長10・softness 1・距離0では標準のratioは0、
C++・Bifrost・研究用exprespyのratioは1でした。
位置には距離0が掛かるため、これだけで位置が増幅することはありません。
native側は距離とsoftnessに1e-6の下限を使います。標準はsoftness 0でhard limitを使い、
距離0では分母を置換して除算を避けます。通常距離の照合成功を、ゼロや微小領域まで
全バックエンドの仕様が同一という意味では扱いません。

算術はdoubleノードへ変更しましたが、``condition`` のfloat出力や極微小領域での
``1 - exp`` の丸めは残ります。全入力で数学的な倍精度一致や残差の解消を保証するものではありません。
有限性・倍率上限・参照値との許容誤差内の一致を検証しています。

Maya標準RP solverの原点近傍の制限
----------------------------------------

長さ5cm＋5cmの最小3ジョイントRP chainとLimbRigのLOD 0を192条件で比較し、
両構成の出力差は最大2.33e-16でした。距離0.01cmの目標に対して終端距離がほぼ0になる挙動も一致しました。
既定のsolver toleranceでは、距離0.01cmのtipとhandleの誤差は約0.0100000184cmでした。
worldMatrix・xform・dgdirty・currentTimeで読み直しても結果は同じで、骨長も維持されています。
倍率が正常でも、このMaya標準RP solverの到達精度の制限は残ります。

共有 ``ikRPsolver.tolerance`` の既定値は1e-5です。値を下げると改善する条件もありますが、
全ての微小距離を解決せず、向きが誤る反例もあるため、製品はsolver設定を変更しません。
Soft IK倍率の修正と、Maya標準RP solverの到達精度を分けて扱います。
