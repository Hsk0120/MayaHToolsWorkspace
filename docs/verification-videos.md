# Maya検証動画の記録とGoogle Drive保存

動画は`.maya-output/verification/<実行ID>/`へ生成し、Google Driveへ保存します。MP4と画像連番はGitやGitHub Pagesへ登録しません。Sphinxには選んだ動画の説明・サムネイル・Driveの閲覧リンクを掲載します。

## 標準ワークフロー

Codex・Claude Code・GitHub Copilotは、リグ検証成果物を「専用シーンで検証リグ作成 → Maya内で計算式と数値を表示 → 実動画を録画・確認 → Google Driveへ保存・リンク共有」の順序で作成します。各エージェントの指示Markdownにも同じ方針を記載しています。

計算表示には、式だけでなく変数の意味・単位・角度の基準・固定値・毎フレームの入力値と実際のDG出力を含めます。固定の値が変わるような演出はせず、変化する値のみ更新します。MayaのHUD等を対象modelPanelへ表示し、完成MP4で可読性・表示の更新・境界での停止と復帰を確認します。`tools/demo_top_view_tangent_limit.py`が実装例です。

ユーザーがローカルのみ等を指定した場合はその指示を優先します。Drive機能が使えなくてもローカル録画まで進め、未完了の工程を明記します。録画・アップロードと、Sphinxへの掲載・コミット・プッシュは別工程です。

## 録画

`tools/verification_video.py`の`recordVideo()`は、表示中のmodelPanelから各フレームをMayaの`M3dView.readColorBuffer`で記録します。検証用コールバックが姿勢更新と数値判定を担当します。画面全体や操作UIの録画は対象外です。

```python
from verification_video import recordVideo

def evaluate(frame):
    # 検証シーンを更新し、実際の数値判定を返す。
    return {"frame": frame, "ok": True}

folder = recordVideo(
    "検証名", 120, 24, "対象modelPanel名", evaluate,
    ffmpeg=r"C:/path/to/ffmpeg.exe",
)
```

`evaluate`によるシーン変更の復元は呼び出し側で行います。共通処理は元のcurrentTimeを復元し、失敗時にも結果JSON・HTMLと取得済みフレームを保存します。全フレームの`ok`が明示的にTrueの場合のみ数値検証成功とします。

FFmpegは`libx264`を含むものを指定してください。出力はH.264/yuv420p/faststartの1280×720 MP4です。再生fpsは検証内容に合わせます。実行日時・Maya版・Gitコミット・未コミット変更の有無・映像SHA-256・各フレームの診断も残します。

## Drive保存と共有

### 上面だけの簡易検証

ユーザーの接線停止の意図に合わせた最新検証は`tools/demo_top_view_tangent_limit.py`です。専用GUIで新規シーンを作り、円に当たらない方向は維持し、円へ入る回転だけを接線角で止めます。左右の停止と復帰を469フレーム、24fpsで示します。円半径3cm・肘の距離4.5cmは固定し、薄い線の表示余裕として半径へ0.03cmを加え、限界角を`180 - asin((3 + 0.03) / 4.5)`度で計算します。標準clampと2つのunitConversionで回転を制限し、実行時のPythonやメッシュ接触検索は補正へ使用しません。円と根元距離が変化する一般リグ向けAPIはまだ実装していません。入力は外向き0度を基準に-180〜180度の範囲で検証しています。保存シーンは`top-tangent-stop.ma`です。

以下の`demo_top_view_root_limit.py`は、外向きcone補正との比較用の旧検証です。

専用Maya GUIで`tools/demo_top_view_root_limit.py`を実行すると、新規シーンを作成します。既存シーンを破棄するため、作業中のMayaへは送らないでください。胴体はXZ平面上の半径3cmの円、肘は円中心から4.5cmの点、尻尾は12cmの方向線です。カメラは上面の固定正投影で、腕位置と尻尾方向のY軸回転だけを動かします。

赤が未補正、緑が補正後、青が曲げた腕です。円への線分交差は録画時の検証にのみ使用します。補正は既存のRootDirectionLimitの標準DGを使用し、交差検査の結果は接続しません。325フレーム、24fpsの正方形動画と`top-view.ma`を実行フォルダへ保存します。

接続済みGoogle Driveプラグインを使うエージェントは以下の順序で保存します。アップロードは録画実行とは別の処理であり、このPythonスクリプト単独ではクラウドへ送信しません。

1. 生成結果が成功しているか確認する。失敗した動画を共有する場合は失敗と明記する。
2. `google_drive_upload_file`でその実行の`verification.mp4`だけを指定フォルダへアップロードする。日時を含む名前にし、既存動画を上書きしない。
3. Driveでその動画を「リンクを知っている全員・閲覧者」に設定する。一般公開共有を扱えないコネクターの場合はDriveの共有UIを使用する。メールによる招待は不要。
4. `google_drive_get_file_metadata`で`id,name,mimeType,size,md5Checksum,webViewLink,permissions`を読み戻す。
5. そのメタデータをローカルJSONへ保存し、`attachDrive`で検証結果へ登録する。

```powershell
python tools/verification_video.py .maya-output/verification/<実行ID> .maya-output/verification/drive-metadata.json
```

`attachDrive()`は形式・サイズ・ローカルSHA-256を確認し、Driveが返したURLを`result.json`、`index.html`、`drive-link.rst`へ保存します。md5Checksumを取得できた場合はDrive側との一致も検査します。公開権限の読み戻し結果は`drive.link_viewer_verified`へ記録します。Falseの場合はリンク共有の完了を報告しないでください。

コネクターの接続認証をローカルスクリプトへ流用したり、トークンをGitへ保存したりしません。通常のPythonのみで自動アップロードする運用は、別途Drive OAuthの初期設定が必要です。

## 肘の位置が動く接線停止サンプル

固定位置の`tools/demo_top_view_tangent_limit.py`と保存済み動画・シーンは残し、別の`tools/demo_top_view_moving_tangent.py`で肘移動を検証します。専用GUIへ送信すると新規検証シーンを作り、入力をキー化して動画と`moving-tangent-stop.ma`を保存します。録画には同じFFmpeg環境変数を使用します。

円の中心を原点として`d=sqrt(x*x+z*z)`、外向きの角度を肘の位置から求め、`limit=180-degrees(asin((r+gap)/d))`を更新します。入力角度から外向き角度を引いて-180〜180度へ折り返し、`output=outward+clamp(relative,-limit,limit)`を計算します。実DGでは平方根・angleBetween・condition・clamp・単位変換等の標準ノードを使用し、保存シーンの補正にPythonやコリジョン検索は不要です。Maya HUDには距離・基準方向・相対入力角度・制限角度・実出力を表示します。

対象はXZ平面、固定円半径3cm、余裕0.03cm、無スケール、根元が半径と余裕の和より外側にある状態です。距離3.4〜7cm、円周上の移動、左右の接線停止と安全方向への復帰を検証します。根元自体が円の内側に入る場合は回転だけでは回避できません。相対入力が±180度を越えると最近接の接線側が切り替わるため、その境界での連続回転を保証する仕様ではありません。短い尻尾でも長い棒としての制限を使用します。

## 腕のローカルX軸だけで回すジョイントサンプル

`tools/demo_joint_twist_tangent.py`は既存の固定位置・移動位置サンプルを残した別検証です。腕軸は`armTwistAxis_JNT`のローカルX、尻尾はその子の`tailRequested_JNT`と`tailCorrected_JNT`からローカルYへ伸ばします。補正は`tailCorrected_JNT.rotateX`だけへ接続し、rotateY/Zは0でロック、根元位置・jointOrientは変更しません。腕自体の移動・傾きは入力です。保存シーンは`joint-twist-tangent.ma`です。

体を半径3cmの球で近似します。球中心を腕ローカル空間へ変換した座標を`c=(cx,cy,cz)`、余裕込み半径を`R=3.03`として、尻尾が回るYZ平面との断面半径は`rho=sqrt(max(0,R*R-cx*cx))`、断面中心までの距離は`dYZ=sqrt(cy*cy+cz*cz)`です。`limit=180-degrees(asin(rho/dYZ))`と、断面中心から離れる方向の角度で、前の接線停止と同様に相対入力を制限します。`R*R-cx*cx<=0`なら回転平面と球内部は交わらないため、入力をそのまま出力します。実DGでは標準angleBetween・pointMatrixMult・演算・condition・clamp・単位変換を使用します。球近似の幾何計算であり、メッシュのコリジョン検索は補正へ接続しません。

前提は根元が球の余裕込み半径より外側、無スケール、尻尾が腕Xに垂直な直線、補正ジョイントのjointOrientが0であることです。腕のjointOrientZ=90度を含む親姿勢に追従し、腕傾斜0・±25・60度を検証します。実体の形状や曲がった尻尾の全頂点を保証する汎用APIではありません。相対角度±180度の接線側切替には連続性の保証がありません。HUDは録画用Pythonで更新するため、保存シーンを単独で開いた際のHUD再作成は別途必要です。保存した補正DGと入力アニメーションはPythonなしで再生できます。

`demo_joint_twist_tangent.main(topView=True)`は同じ入力・補正を上面の固定正投影で録画します。既定の斜め版と別の実行フォルダへ保存し、上面版の最新フォルダは`.maya-output/verification/latest-joint-twist-top.json`に記録します。腕の傾斜を含む3D動作なので、上面で円と重なって見えても高さ方向で離れている場合があります。

## 肘側へ固定する接線

`demo_joint_twist_tangent.main(topView=True, fixedElbowSide=True)`は、黄色の`elbowDirection_JNT`が示す曲がり側を初期姿勢で選び、その接線側を維持します。緑が固定側、橙が従来の最近接側、赤が入力です。既存モードと保存済み動画は保持し、`joint-twist-fixed-elbow.ma`と`latest-joint-fixed-elbow.json`を別の実行フォルダへ保存します。

腕ローカルYZ平面での外向きを`n=(ny,nz)`、肘ガイド方向を`h=(hy,hz)`とすると、正回転側の接線方向は`(-nz,ny)`です。初期の内積`(-nz)*hy+ny*hz`の符号を`side`として記録します。このサンプルではガイドを腕ローカル-Zへ置き、side=+1となります。肘のガイドが側を判定できない方向なら作成を拒否します。球の断面・制限角度は従来と同じです。

相対入力を`relative=wrap(input-outward)`として、断面があり`abs(relative)>limit`なら`output=outward+side*limit`、それ以外は`output=input`です。中心方向±180度をまたいでもsideを変更しないため、最近接側の切替は起きません。過去フレームの状態は使わず、任意の時刻へ移動しても同じ結果です。回避先を毎フレーム肘ガイドから選び直す実装ではありません。

安全な入力を維持するため、優先側とは反対の安全方向から危険範囲に入る・抜ける境界では不連続になり得ます。中心方向の切替を解消する方式であり、全360度での連続性を保証しません。実際の肘の曲がり方向に合わせるには、初期ガイドの配置を調整します。腕ローカルXだけの補正・球近似・根元球外等の前提はジョイント版と同じです。

## 固定側のフリップ再現

`demo_joint_twist_tangent.main(topView=True, fixedElbowSide=True, reproduceFlip=True)`は、固定側とは逆の安全境界を横切る条件を別の動画へ保存します。A:入力44〜40度、B:距離4.3〜4.7cmで入力43度固定、C:円周上の肘位置角-2〜+2度で入力43度固定、D:腕傾斜0〜25度で入力40度固定を往復します。最後に中心方向の入力-10〜+10度を往復し、固定側が切り替わらない比較も入れます。保存シーンは`joint-fixed-side-flip-repro.ma`、最新ポインタは`latest-joint-flip-repro.json`です。

side=+1の場合、不連続となる境界は`relative=-limit`です。安全側の出力`outward-limit`から危険側の出力`outward+limit`へ切り替わります。円上で見た最短の跳び角は`360-2*limit=2*asin(rho/dYZ)`度です。距離4.5cm・断面半径3.03cmなら約84.65度で、入力を少しだけ変えても大きく跳びます。入力だけでなく、肘移動や腕傾斜でoutward/limitが変化しても同じ条件を満たします。

HUDにケース名・逆側境界・制限角・出力角と1フレームの回転差を表示します。回転差は360度の表示折り返しを除いた値で、30度を超えるとFLIPを1秒表示します。録画の`ok`は非交差・式との一致・1軸保持を意味し、滑らかさの成功判定ではありません。フリップを意図的に含む再現動画です。

## フリップより貫通を許容する連続制限

`demo_joint_twist_tangent.main(topView=True, fixedElbowSide=True, reproduceFlip=True, continuousElbowSide=True, maximumAngle=60)`は、旧固定側の再現入力を使い、緑の出力を肘側の負回転可動域だけへ制限します。橙は旧固定側の出力です。このジョイント配置では肘側が負回転なので、プラス方向へは切り替えません。最大角は度で0より大きく180未満です。既存の非貫通モードは維持します。

初期尾の+Y方向と選択接線方向の無符号角を`a`として、`bound=-min(maximumAngle,a)`、`output=clamp(input,-maximumAngle,bound)`を標準DGで計算します。無符号角はangleBetweenで0〜180度として求め、±180度の数値折り返しを使いません。安全/危険で接線と入力を切り替える分岐はなく、角度の境界で出力が連続につながります。球の断面がなくなっても可動域制限を維持し、入力への突然のbypass復帰を作りません。

これは片側可動域と連続性を優先する代替方針です。すでに安全な入力も範囲外なら制限し、任意の肘位置で元の接線と同じ方向を保証する方式ではありません。回避に60度を超える回転が必要なら-60度で止め、貫通を許容します。動画末尾に距離3.2cmの上限到達とBODY HITを表示します。`ok`は計算式・1軸保持の検証であり、非貫通の成功を意味しません。球近似・腕軸に垂直な直線尾・無スケール・根元球外等の前提は維持します。保存は`joint-continuous-elbow-cap.ma`、最新フォルダは`latest-joint-continuous-cap.json`です。

## 尻尾1軸回避の方式比較（横並び）

`demo_joint_sweep_compare.main()`は、方式ごとに列を分け、同じ入力アニメーションで横並びに比較します。左から入力・従来・外側を回す・先回り・コーン押し出しの5列です。各列に体・腕・入力尾（赤）・補正尾があり、補正は腕ローカルXの`rotateX`だけを標準DGで計算します。外向きを0度とした相対角`rel`、接線角`L=180-asin(rho/d)`、禁止範囲の半幅`h=180-L`を共通に使います。

- 従来（橙）: `clamp(rel,-L,L)`。`rel=±180`で左右が入れ替わりフリップします。貫通はしません。
- 外側を回す（緑）: `|rel|<=L`は入力のまま、禁止範囲では`L(180-|rel|)/(180-L)`で外側を通って反対側の接線へ運びます。その区間は約`L/(180-L)`倍の速さで回ります。
- 先回り（水色）: 頂点`P=1.5L-90`、傾き`k=P/(180-P)`、つなぎ幅`w=0.25(180-P)`。`|rel|<=P-w`は入力のまま、その先は二次曲線で折り返して速さを抑えます。
- コーン押し出し（マゼンタ）: 中心方向からの角度`u=180-|rel|`で、`u<=h`は重み1、`u>=h+30`は0、間はsmoothstep。出力は`rel+1.15h*w`で常に+側へ押します。フリップせず変化もなだらかですが、+側から体へ近づくと貫通します。

緑・水色・コーンはいずれもフリップしません。ただし1軸の回転で入力が体の周りを一周する限り、「折り返して速く回る」「片側から貫通する」「左右が切り替わる」のどれかは避けられません。また、腕を傾けて体が回転平面から外れる瞬間は、緑・水色が速く回ります。録画の`ok`は計算式との一致・1軸保持、緑と水色の非交差を意味し、従来とコーンの貫通は許容しています。保存は`joint-sweep-compare.ma`、最新ポインタは`latest-joint-sweep-compare.json`です。

## 尻尾1軸回避: 入った側の接線を保持

`demo_joint_side_keep.main()`は、従来の「接線で止める」挙動のまま、中心を越えたときのフリップをなくす方式を、入力・従来・新方式の3列で比較します。

- 従来（橙）: 相対角を`-180〜180`に折り返してから`clamp(rel,-L,L)`します。折り返しによって、中心（`rel=±180`）を越えた瞬間に左右の接線が入れ替わります。
- 入った側を保持（緑）: 外向きの角度を`180+atan2(cz,cy)`として連続に求め、相対角は折り返さずに`clamp(rel,-L,L)`します。
  - +側から入った場合、`rel`は`L`を超えて増え続けるので、+側の接線に止まり続けます。
  - −側から入った場合は、−側の接線に止まり続けます。
  - 状態を持たないので、タイムラインのどこへ飛んでも同じ結果になります。

制限は次の3点です。

- 入力を中心よりさらに回し、反対側の安全範囲まで抜けても、入った側の接線に止まったままです。入力を戻せば離れます。録画の「8 KEEP TWISTING +」がこの場面です。
- 外向きの角度は、体の中心が腕Yの+側にある前提です。腕から見て体が`cy<=0`側へ回り込むと不連続になります。
- 回転平面と体が交わらない間は入力を通します。巻き付いた状態（`|rel|>L`）のまま交わりが消えると、その瞬間に入力の向きへ戻ります。

録画の`ok`は、両方式の計算式との一致、1軸保持、非交差を意味します。保存は`joint-side-keep.ma`、最新ポインタは`latest-joint-side-keep.json`です。

## 尻尾1軸回避: 身体固定コーンでなだらかに避ける

`demo_joint_cone_soft.main()`は、身体に固定した向きのコーンへの入り具合で`rotateX`をなだらかに避ける方式を、入力・球の接線止め（入った側を保持）・身体固定コーンの3列で比較します。コーンは身体空間`-X`を軸とする半角`γ=40°`の向きだけのコーンで、肘の位置は使いません。黄色の線がコーンの軸と境界です。

- コーン軸を腕空間へ変換した`(ax, ay, az)`から、`s=√(ay²+az²)`、回転面でのコーン中心`θa=atan2(az, ay)`、回転面を切る半幅`h=acos(cosγ/s)`を求めます。`s<=cosγ`ならコーンは回転面に届かず`h=0`です。
- 外向き`θo=θa+180`を基準に、折り返さない相対角`rel=rx-θo`、境界`L=180-h`、ブレーキ幅`m=min(40,h)`、`start=L-m`を使います。
- `|rel|<=start`は入力のまま、その先は`start+m*depth/(depth+m)`（`depth=|rel|-start`）とし、`L`に近づくだけで越えないので、コーンには入りません。符号は入ってきた側を保ちます。
- 身体が回るとコーンも回ります（録画の「8 BODY TURNS」）。

制限: コーンは向きだけで判定するので、肘が体に近づいたり体の中心からずれたりしても避ける範囲は変わりません。録画の「6 ELBOW MOVES」では、肘が近く斜めの位置にあるときに25フレーム球と交差します。必要ならコーン角を肘の距離で広げる補正を足します。録画の`ok`は計算式との一致・1軸保持・球列の非交差・コーン列がコーンに入らないことを意味します。保存は`joint-cone-soft.ma`、最新ポインタは`latest-joint-cone-soft.json`です。

## 尻尾1軸回避: UE RBFのポーズ補間

`demo_joint_rbf_pose.main()`は、補正を計算式で直接求める代わりに、MetaHuman for Maya同梱の`MayaUERBFPlugin`（`UERBFSolverNode`）でポーズを補間する方式を、入力・球の接線止め・UE RBFの3列で比較します。プラグインは実行時に明示的にロードします。初回は専用GUIで「信頼されていない場所」の確認が出るので、手動でAllowします。

## 尻尾1軸回避: hip〜l_lowerArmのチェーンと3球の体

`demo_joint_chain_rbf.main()`は、hip・spine0〜2・l_shoulder・l_upperArm・l_lowerArmのチェーンを周期の違う正弦波で同時に動かします（背骨のひねり・曲げ、肩の上げ下げ、腕の振り、肘）。体はhip・spine1・spine2に付けた3つの球です。入力・3球の接線止め・UE RBFの3列を正面から比較します。

- 球ごとに、回転面を塞ぐ範囲`[θ-asin(ρ/d), θ+asin(ρ/d)]`を求めます（`θ=atan2(cz,cy)`）。交わる球の範囲をまとめて下限A・上限Bとし、中心`c=(A+B)/2`、半幅`H=(B-A)/2`、外向き`c+180`、接線`L=180-H`とします。左右で幅が違う体にも対応します。
- 接線止めは`clamp(rel,-L,L)`、UE RBFはドライバー`(rel/20, H/10)`の385ポーズ（`H=0〜100`）です。どちらも折り返さない`rel`を使うので、入った側を保ちます。UE RBFの範囲は、下の「球の交わり始めをなだらかに効かせる」方法で求めます。
- UE RBFのドライバーは専用ジョイント`<列>RbfDriver_JNT`です。translateXに`rel/20`、translateYに`H/10`をつなぎ、その`matrix`をソルバーの`inputs[0]`へ渡します（MetaHumanのPose Editorがジョイントをドライバーにするときと同じつなぎ方）。ジョイントは列の左下の「ドライバー空間」グループに置き、ポーズの格子（rel 20度刻み×H 10度刻み、白い縦線がrel=0）と一緒に表示します。スケルトンのジョイントの回転を直接ドライバーにすると、クォータニオンの比較で190度と−170度が同じになり、入った側が消えてフリップが戻るため使いません。計算で作った行列をつないでいた版と、出力は全541フレームで一致しました（差0.0度）。
- 出力側はMetaHumanのPose Editorと同じ構成です。各ポーズに`rel-040_H070`のような名前を付け、前腕の下の外向きで回るグループ`<列>TailOutward_GRP`にあるドリブンジョイント`<列>TailDriven_JNT`を`UEPoseBlenderNode`（`<ドリブン>_UEPoseBlenderNode`）で回します。ポーズの値はX軸まわりの回転行列で、メッセージ接続（`drivenTransform`→`poseBlender`、`poseBlenders`→`rbfSolver`）・`weights[i]←outputs[i]`・`outMatrix`→`_dmt`→ドリブンのTRSのつなぎ方もPose Editorと同じです。尻尾の出力は`外向き + clamp(ドリブンのrotateX, -L, L)`です。
- Pose Editorでは、ソルバーを選んで「Edit Selected」→ポーズを選ぶ（ドリブンがそのポーズの角度になる）→ドリブンを回す→「Update」→編集終了で、そのポーズの値を直せます。確認では`rel-040_H070`を−40度から−55度に変えると、そのポーズの近くの200フレーム目の尻尾が137.5度から128.1度に変わりました。ドライバージョイントはrelとHから計算した値がつながっているので、「ポーズへ移動」しても動きません（ポーズは名前で選びます）。

- この互換性は`tools/verify_pose_editor_rbf.py`の`main()`で再確認できます（HToolsの「rigging > tailAvoidanceSamples」の「Checks > Run check」からも実行可）。回転ベースのドライバーは`main(case="rotation", prefix="rot")`です。チェーンのシーンを組み、`metahuman_for_maya.mod`の`PYTHONPATH`・`PATH`を追加してPose EditorのAPIで、ソルバー・ドライバー・ドリブンの認識、全ポーズの名前、編集モード→ポーズへ移動→ドリブンを回す→Update→編集終了での値の保存と尻尾の出力の変化、編集後の接続の復帰、画面の表示の11項目を確かめます。結果は`.maya-output/verification/<実行ID>/pose-editor-check.json`とInputs・Posesタブの画像（最新は`latest-pose-editor-rbf.json`）で、1項目でも満たさなければ例外になります。

制限: 球が回転面と交わり始めた瞬間に、その球の中心角が今の範囲の外にあると、範囲が広がって出力が跳ぶことがあります（今回の動きでは3球が常に交わっていたため発生していません）。離れた球どうしの間のすき間も、塞がれた範囲として扱います。正面からの投影なので、奥行きのある姿勢では尻尾が球に重なって見えることがありますが、交差判定は3Dで行っています。保存は`joint-chain-rbf.ma`、最新ポインタは`latest-joint-chain-rbf.json`です。

### 球の交わり始めをなだらかに効かせる（跳びの対策）

`demo_joint_chain_rbf.main(case="soft_entry")`は、上の跳びの場面を「直す前（そのまま合わせる）」の接線止め、「直した後」の接線止め、「直した後」のUE RBFの4列（入力を含む）で比較します。UE RBFは、すべてのケースでこの方法を使います。

- 回転面が球に入り込んだ深さの割合`q=(R+gap-|cx|)/(R+gap)`（掛かり始め0、中心で1）から、重み`w=smoothstep(q/0.25)`を求めます。
- 球を範囲へ足すとき、足す前の範囲と、足した後の範囲`[min(A,θ-半幅), max(B,θ+半幅)]`を`w`で混ぜます。最初の球は、半幅に`w`を掛けて始めます。
- 断面の半径`ρ`は掛かり始めに急に増えるので、重みには使いません。

結果（太ももの球が交わる場面）:

| 方式 | 1フレームの最大変化 | 移る長さ | 食い込み |
|---|---|---|---|
| 直す前 | 24.6度 | 1フレーム | なし |
| 直した後（`q/0.25`、既定） | 11.5度 | 約3〜4フレーム | 26フレーム・最大0.18cm |
| 直した後（`q/0.5`） | 8.4度 | 約8フレーム | 121フレーム・最大0.42cm |
| 直した後のUE RBF（`q/0.25`） | 10.5度 | 約3〜4フレーム | 2フレーム・最大0.07cm |

UE RBFは、ポーズの値が接線の手前で止まる（なだらかに避ける）ので、接線止めより食い込みが少なくなります。

尻尾が移る角度の合計（約60度）は変わらず、数フレームに分けて動かします。分ける時間を長くするほど、浅く掛かっている間の食い込みが増えます。`SOFT_FULL`でこの釣り合いを調整します。録画の`ok`は独立計算との一致・1軸保持・RBFの重み合計、直す前の列の非交差を意味し、直した後の列の食い込みは記録のみです。保存は`joint-chain-soft-entry.ma`、最新ポインタは`latest-joint-chain-soft-entry.json`です。

### 前半を肘からのコーンで近似する

球は肘から見ると、頂点が肘、軸が球の中心方向、半角`asin((R+gap)/距離)`のコーンになります。このコーンを尻尾の回転面で切った半幅`acos(cosγ/s)`（`s`は軸の回転面への投影の長さ）は、球の断面から求めた`asin(ρ/d)`と一致します。つまり球の計算は、距離に応じて角度が自動で変わるコーンドライバーと同じです。

`demo_joint_chain_rbf.main(case="cone_c")`は、後半を同じUE RBF（なだらかに効かせる対策あり）にして、前半だけを入れ替えた4列を比べます。

- A（球）: `γ=asin((R+gap)/d)`。
- C（固定角のコーン）: `γ=γ0`。`γ0`は初期姿勢の距離`d0`での`asin((R+gap)/d0)`です。
- C（距離で補正したコーン）: `γ=γ0·d0/d`。

コーンの角度は`composeMatrix`（Z軸まわりに`γ`回転）と`vectorProduct`で`cosγ`にしてから使います（標準ノードにcosがないため）。掛かり具合は、軸と回転面のなす角`e`から`q=(γ-e)/γ`で求めます。

一般的なコーンドライバーの出力（向きがコーンにどれだけ入っているかの0〜1）は、左右の区別も接線の位置も持たないので、RBFのドライバーには使いません。録画では参考としてHUDに表示します（入力の尻尾で0〜0.95）。

結果（チェーンの複雑な動き、541フレーム）:

| 前半 | 球との半幅の差 | 球の列との出力の差 | 食い込み | 中心付近の最大変化 |
|---|---|---|---|---|
| A 球 | 0 | 0 | なし | 0.55度 |
| C 固定角 | −3.2〜+21.4度 | 最大19.0度 | なし | 1.32度 |
| C 距離で補正 | −0.6〜+7.7度 | 最大2.0度 | なし | 0.94度 |

距離の補正を接線の一次近似`γ0+k(d0-d)`にすると、`asin`が距離に対して下に凸なので、どの距離でも角度が小さくなりました（半幅が最大19度小さい）。比`γ0·d0/d`なら、遠ざかると少し大きめ（安全側）です。固定角は、初期姿勢（肘が体に近い）の角度のままなので、離れたときに避けすぎます。保存は`joint-chain-cone-c.ma`、最新ポインタは`latest-joint-chain-cone-c.json`です。

### ConeReaderの0〜1をRBFのドライバーにする

`demo_cone_rbf.main()`は、`mlrig.setups.ConeReader`の出力（0〜1）だけをUE RBFのドライバーにした版（D）を、幾何の角度`(rel, H)`をドライバーにした版（A）と、チェーンの複雑な動きで比べます。

- Dは、尻尾の入力の向き（ローカルY）を矢印にしたConeReaderを3つ置き、コーンを胸（spine2）に追従させます。1フレーム目の姿勢で、体の中心方向（半角`H+20`）と左右の接線方向（半角80）へ向けます。
- RBFのポーズは、1フレーム目の姿勢で尻尾を5度刻みで一周させ、3つのweightと、接線で止める補正量（出力−入力）を組にした72個です（Additive・ガウス・半径0.1）。
- 左右のコーンを半角30にすると中心まで届かず、中心の左右で3つのweightが同じになって補正が平均され、1フレーム目でも最大70度ずれました。

結果（541フレーム）:

| | A（rel, H） | D（ConeReader×3） |
|---|---|---|
| 食い込み | 0 | 195フレーム、最大2.43cm |
| 中心付近に留まる間 | 食い込みなし、最大変化0.55度 | 120フレーム中118で食い込み、最大変化23度 |
| 最大の1フレーム変化 | 19.1度（入力の速さ） | 70.2度（中心を越えるときのフリップ） |
| 学習した姿勢から遠い | — | 3フレームで重みの合計がほぼ0（補正なしにした） |

0〜1は向きに対して連続で、左右と「どちらから入ったか」を持ちません。正しい補正は中心をはさんで＋側から−側へ切り替わるので、RBFはそれを平均でつないで中心付近で体に入ります。また、コーンの向き・角度は1フレーム目の姿勢で決めたまま変わらないので、肘と体の距離や向きが変わると補正がずれます。1フレーム目の姿勢ではAとの差は0です。ConeReaderの0〜1は「どれだけその向きに近いか」で補正形状などを駆動する用途に向き、この尻尾の接線止めには、幾何の角度をドライバーにする方が適しています。保存は`cone-rbf.ma`、最新ポインタは`latest-cone-rbf.json`です。

### 簡易版：ConeReader 2つとUE RBF

`demo_simple_cone_rbf.main()`は、rel・Hの計算を使わない簡易版を、今の仕組み（rel・H＋385ポーズ）と比べます。

### 案1（体基準の空間のコントローラー）と案2（ターゲット）

`demo_space_target.main()`は、rel・Hを計算しない2案を、今の仕組みと4列（入力・今の仕組み・案1・案2）で比べます。

- 共通: 前腕の下に、お腹の球へ`aimConstraint`で−Yを向けるグループを置きます（rotateXだけ、+Yが体と反対の向き）。尻尾の出力はこのグループの下です。止める角度Lは、肘とお腹の球の距離からドリブンキー（6キー）で決めます。キーは、この動きの中で距離ごとに一番広く3球が塞いだ範囲（Hの最大+5度）から作り、L=180−Hです（距離3.5〜6.2cmでLは101〜129度）。
- 案1: グループの下のコントローラーの rotateX が、そのまま「体の反対向きから何度回したか」です。rotateXは一周を超えても数え直さないので、入った側を保ちます。尻尾は`clamp(コントローラー, -L, L)`です。
- 案2: アニメーターはターゲット（ロケーター）を動かし、グループから見たターゲットの方向の角度（−180〜180）を`clamp(角度, -L, L)`にして尻尾を向けます。デモではターゲットを入力の尻尾の先端に置いています。

結果（541フレーム、中心を何度も越える入力）:

| | 今の仕組み | 案1 | 案2 |
|---|---|---|---|
| 食い込み | 0 | 0 | 19フレーム（最大0.21cm） |
| 1フレームの最大変化 | 19.1度 | 19.0度 | 155度（ターゲットが体の真裏を越えると反対側へ切り替わる） |
| 中心付近に留まる間の最大変化 | 0.5度 | 0.3度 | 135度 |
| 今の仕組みとの差 | — | 平均2.8度・最大11.7度（余裕の分だけ手前で止まる） | — |

案1は、部品（aimConstraint・distanceBetween・ドリブンキー・clamp）が少なく、フリップもしません。コントローラーが体を基準に回るので、腕や体が動くと、アニメーターが触らなくても尻尾は体に対して同じ向きを保とうとします。Lは左右で同じ値なので、体が左右非対称なら広い側に合わせる必要があります。今回のドリブンキーはこの動きから作ったので、動きの範囲を超える姿勢では見直しが必要です。案2は切り替わりが目に見える代わりに、中心を越える入力ではそのたびに反対側へ切り替わり、左右非対称の体では切り替わった側で食い込みました。保存は`space-target.ma`、最新ポインタは`latest-space-target.json`（ドリブンキーの値も記録）です。

### 案1の実行時版（尻尾は動かさず、腕の動きで自動で避ける）

`demo_runtime_avoid.main()`は、尻尾を前腕に対する決まった向き（rotateX = rx0 = 90度）に固定したまま、shoulder・upperArm・lowerArm（前腕のひねり ±100度を含む）を大きく動かし、体が尻尾の向きを越えて回ってくる場面で、尻尾が実行時に自動で避けるかを確かめます。比べる列は、入力（避けない）・今の仕組み（尻尾の入力をrx0に固定）・案1の実行時版です。

- 前腕の下のグループを、お腹の球へ`aimConstraint`で+Yを向けます（rotateXだけ、上方向は前腕のX軸）。グループのrotateXが、前腕から見た体の方向θです。外向き=θ+180、`rel = rx0 − 外向き`です。尻尾は動かないので、relを変えるのは腕の動きだけです。
- θは、体が前腕の−Y側へ回り込まない限り連続です（この動きでは−129〜128度）。体が尻尾の向きを越えてもrelは−199度と続けて数えられ、押されてきた側を保ちます。
- 止める角度は左右別のドリブンキー（ドライバーは肘とお腹の球の距離）です。お腹から見て体の左右の張り出しが違うためで、距離3.4〜6.3cmでL+は117〜129度、L−は81〜127度になりました（この動きの距離ごとの塞がれた範囲の端+5度）。左右同じLでは21フレーム（最大0.61cm）食い込みました。
- 尻尾の rotateX = 外向き + clamp(rel, −L−, L+) です。部品は aimConstraint・distanceBetween・ドリブンキー2本・plusMinusAverage・clamp だけです。

結果（541フレーム）: 何もしないと185フレーム食い込み（最大2.43cm）、今の仕組みは食い込み0・最大変化22.0度、案1の実行時版は食い込み0・最大変化4.2度でした。案1と今の仕組みの差は平均10.5度（案1は接線ちょうど手前で止め、今の仕組みは手前からなだらかに止めるため）。Lは距離だけから決めているので、腕の傾きなど距離以外の変化が大きい動きでは余裕を大きめにするかキーを見直します。保存は`runtime-avoid.ma`、最新ポインタは`latest-runtime-avoid.json`（ドリブンキーの値も記録）です。

#### 腕を上げる姿勢とConeReaderの切り替え

`demo_humanoid_tail_avoid.main(case="raise")`は、Aポーズ・肘1軸のまま、upperarm_lを腕を上げる姿勢（rotate = 0, −109.263, −125.343 など）まで大きく動かし、入力・案1・案1＋ConeReaderの切り替え2種の4列を真上から比べます。

- 案1だけでは、腕を上げて体が尻尾の回転面から外れても、止める角度が肘と胴の距離だけで決まるので clamp が効き続けます。さらに胴の方向が狙う軸から大きく回ると rel が−180度を越え（例: −281度）、「回り込んだ」と見なして接線に押し付けたままになり、尻尾が肘に付いていきません。
- 切り替えは、当たり判定の球ごとに`mlrig.setups.coneReader.ConeReader`を置き、矢印を前腕のX軸、コーンを肘から球の中心へ向けます（コーンに`aimConstraint`）。球が回転面を切るのは、出力`angle`が90度から asin(r/d) 以内のときです。球ごとの m = |angle − 90| − asin((r+2cm)/d)（asinは距離からのドリブンキー）の最小から w = smoothstep((15 − m)/15) を作り、尻尾の rotateX = rest + w·(clamp(rel, −L−, L+) − rel) にします。w=0なら元の向き、w=1なら案1と同じです。
- 「keep side」は狙う軸を胴が回転面に掛かる姿勢での胴の方向の平均にして入ってきた側を保ち、「near side」は狙う軸を REST_RX+180 にして rel を±180度で折り返し、近い方の接線へ逃げます。L はupperarmの回転を広く振った姿勢（rx −90〜90・ry/rz −150〜150）の標本から作ります。
- 結果（541フレーム）: 入力は90フレーム食い込み（最大15.7cm）。案1・keep side・near side はいずれも食い込み0。確認姿勢（180〜215・485フレーム）では、案1が尻尾を2度（接線）に止めたままなのに対し、切り替えつきの2列はw=0で元の向き（−135度）を保ち、肘に付いていきます。keep side は w が切り替わる数フレームで1フレーム最大30.6度回ります。near side は胴が尻尾の位置を横切るとき反対側の接線へ移り、143〜165度の跳びが3回ありました。保存は`humanoid-tail-avoid-gate.ma`、最新ポインタは`latest-humanoid-tail-avoid-gate.json`です。

#### 尻尾6本の初期ポーズと腕のツイストの打ち消し

`demo_tail_twist_cancel.main()`は、Aポーズの骨格に左右3本ずつの尻尾（upperarmの根元＝upperarmの子、肘＝lowerarmの子、手首の根元＝lowerarmの子）を付け、腕のツイストを打ち消すかを、打ち消しなしと並べて斜め後ろから確かめます。

- 初期ポーズはAポーズで、腕と直角のまま真後ろから下へ30度ひねった向き（rotateX = −120）。右は`jointOrientX = 180`にして、左右とも同じ値で鏡像の向き・回り方にします。
- 打ち消しは、骨の鎖骨から見た初期ポーズからの回転 R = 骨のworldMatrix × 鎖骨のworldInverseMatrix × (初期の同じ積)⁻¹ を`decomposeMatrix`のクォータニオンにし、X成分とW成分だけを`quatNormalize`→`quatToEuler`に通してツイスト角 t を取り出します（スイング・ツイスト分解）。尻尾の rotateX = −120 − t。lowerarm の R には upperarm のツイストも含まれるので、肘・手首の尻尾は両方の骨のツイストを消します。`matrixNodes`・`quatNodes`はMaya同梱のプラグインです。
- 検査はリグと独立に、骨のX軸を初期から今の向きへ最短で回す回転（ツイストなし）を初期の尻尾の向きにかけ、実際の尻尾の向きとの角度差を測ります。
- 結果（361フレーム、upperarmのツイスト±70度・振り・上げ下げと肘の曲げ）: 打ち消しなしは最大97.2度ずれ、打ち消しありは全6本・全フレームで0.0度。リグのツイスト角と独立計算の差も0.0度でした（upperarm −75〜+70度、lowerarm −97〜+93度）。保存は`tail-twist-cancel-wave-back.ma`、最新ポインタは`latest-tail-twist-cancel-wave-back.json`です。
- `main(motion="problem", view="top")`（正面は`view="front"`）は、食い込みが多い姿勢（腕を後ろへ引く・後ろで内側へ回す・前に出して肘を深く曲げる・体に沿って下ろす、保持中に±40度ひねる）を通る動きを真上から、打ち消しなし・スイング・ツイスト分解・ローカル値の3列で比べます。ローカル値は尻尾の rotateX = −120 − (upperarm.rx [+ lowerarm.rx]) で、Eulerの最初に回る rotateX だけを打ち消します。HUDの`BODY HIT`は尻尾の線分と体のプロキシ（左右の腕以外）の交差、`max turn`は尻尾の向きの1フレームの最大変化です。
- 結果（361フレーム、左の尻尾）: 食い込みは、なし＝upperarm 114・手首30フレーム、スイング・ツイスト分解＝upperarm 148・肘21・手首45フレーム、ローカル値＝upperarm 106・手首30フレーム。1フレームの最大変化は、なし8.0度、分解165度（肘を深く曲げた前腕が初期の向きの反対近くまで回ると分解が不安定になり、肘・手首の尻尾がくるくる回る）、ローカル値9.4度でした。
- `main(motion="cross")`は、肘を−110度（後半は−95度）に曲げたまま upperarm の rotateX を0→170→0（後半は0→120→0）とひねり、同じ側の尻尾どうしの線分の最短距離をHUDに出します（1cm未満で`CROSS!`）。結果（361フレーム、左）: 打ち消しなしは尻尾が腕と一緒に回るので最短31cmで交差しません。打ち消しあり（分解・ローカル値とも、rotateXだけのひねりなので同じ）は upperarm の根元と手首の根元の尻尾が95フレーム（141〜333）交差し、最短0.02cmでした。upperarmの尻尾は打ち消しで止まり、手首の尻尾は曲がった前腕ごと upperarm の軸のまわりを回ってくるためです。
- 交差を防ぐ案（`motion="cross_fix"`・`"problem_fix"`）: upperarmの尻尾はローカル値の打ち消しのまま、肘・手首の尻尾にスイング（骨に沿う傾き）を足す3案をローカル値と並べます。A「平行」はupperarmの尻尾の向きを狙う点へ`aimConstraint`（上方向は前腕のX軸なので、前腕の軸まわりのひねり＋骨に沿う傾きの2軸）、B「スイングのみ」はひねりをローカル値のまま、傾き＝(upperarmの尻尾と前腕のX軸のなす角)−90度を±60度に制限して rotateZ（回転順 zyx）へ、D「肘の曲げの打ち消し」はひねりをローカル値のまま、肘の曲げ（lowerarmのrotateY）を尻尾のrotateYで打ち消します（左は −肘の曲げ、右は jointOrientX = 180 なので +肘の曲げ）。回転順 xyz なので「upperarmのひねり → 肘の曲げ」を逆順に戻すことになり、尻尾の3軸がupperarmの尻尾と一致します（Aと同じ向きで、ノードは符号を変えるunitConversionを1つ足すだけ）。`build()`の`"half"`（ローカル値の向きとAの向きの二等分）も残してあります。
- 結果（左、361フレーム）: 交差する動きでは、upperarmと手首の尻尾の交差がローカル値95フレーム・A 0（最短19.1cm）・B 4・D 0フレーム（C「半分」は89フレーム）、upperarmと肘はBだけ29フレーム交差しました。食い込みが多い姿勢の動きではどの案も交差なし、手首の尻尾の体への食い込みはローカル値・B 30フレーム、A・D 69フレーム。AとDはすべての数値が一致し、手首・肘の尻尾とupperarmの尻尾のなす角は左右とも全フレームで0.0度でした。Aは肘を−90度・upperarmのrotateXを−30度にすると（腕の向きによらず）upperarmの尻尾の向きと前腕の軸がそろい、手首の尻尾が前腕に沿って肘の方へ向きます。そこを通るとAは尻尾の向きは連続ですが、尻尾の横の軸（ロール）が180度反転します。Dは3軸ともupperarmの尻尾に一致したまま（差0.0度）で、ロールは反転しません。
- 案D＋前腕のConeReader（`motion="align_cone"`・`"cross_cone"`・`"problem_cone"`、3列: ローカル値／D／D＋コーン）: Dの向き d（補助の関節）を矢印、尻尾が骨の中を通る前腕の軸 a（手首の尻尾は −X、肘の尻尾は +X）をコーン（半角25度、なめらか）にしたConeReaderの重み w で、尻尾の向きを (1−w)·d + w·d' へ`aimConstraint`します。d' = cos25°·a + sin25°·L はコーンの縁のうちローカル値の向き L（前腕と常に直角）の側で、w=0ならDと同じです。`align`は肘−90度のまま upperarm の rotateX を +20〜−80度と動かし、Dの手首の尻尾が前腕に沿う姿勢（rotateX ≈ −30）を通ります。
- 結果（左、361フレーム）: `align`ではDの手首の尻尾が前腕の軸から0度（肘の方へ前腕に沿う）まで近づき、肘と手首の尻尾が5フレーム交差しました。D＋コーンは前腕の軸から9度以上離れ、交差なし（最短4.0cm）、平行からのずれは最大25度、1フレームの最大変化2.9度。`cross`ではコーンがほぼ効かず（w最大0.1）、upperarmと手首の尻尾は交差なし（Dと同じ最短19.1cm）。`problem`はDとほぼ同じ（w最大0.03）。なお、前腕の軸に近い d がローカル値と反対側にあると、押し出しの途中で軸に少し近づくことがあり（`cross`で肘の尻尾が20度→15.7度）、最初に試した「肘の曲げの打ち消しを (1−w) 倍にする」方式は、肘の尻尾が前腕に8.6度まで近づき、交差も戻ったため採用していません。
- 案D＋前腕のコーン＋3本共通の体の回避（`motion="problem_avoid"`・`"cross_avoid"`・`"align_avoid"`、3列: ローカル値／D＋コーン／D＋コーン＋体の回避）: Dでは3本の尻尾が平行で、どれも upperarm のX軸に垂直な面の中で同じ角度だけ回るので、1つの回避角 Δ を3本の rotateX に同じだけ足します（twist から Δ を引く）。Δ は`tools/tail_shared_avoid.py`の`buildDelta()`が標準ノードで作ります。upperarm のひねりを打ち消した空間 F（rotateX = −upperarm.rotateX の子）で、胴の方向 τ を rotateX だけの`aimConstraint`で連続に求め、3本の付け根それぞれで当たり判定の球が面を塞ぐ範囲（中心の角度 ± asin(ρ/d)、尻尾が接点まで届かなければ先端が届く角度 acos((ℓ²+d²−ρ²)/(2ℓd))。asin・acosは`remapValue`の曲線）を胴の方向から測り、半幅に応じた重みで胴の方向からつなげた範囲 a〜b にまとめ、案1と同じ clamp（外向きからの角度を [b−180+5, a+180−5]）にします。何も塞いでいなければ Δ = 0。当たり判定の球はプロキシに合わせた大きさ（`AVOID_BODY`、胸15cm・首・頭を含む）で、初期ポーズの尻尾は動きません（Δ = 0）。
- 撮影は上面・正面・パース（斜め後ろの透視投影、`view="back"`）の3視点で、3本を縦に並べた動画にしています。食い込みは付け根から8cmより先（`ROOT_ZONE`）と付け根の近くを分けて数えます。肩の付け根は胸のプロキシの表面から約2cmなので、付け根の近くでは胸の角をかすります（これまでのupperarmの尻尾の「食い込み」はすべてこれでした）。
- 結果（左、361フレーム、8cmより先の食い込み）: 食い込みが多い姿勢の動きで手首の尻尾がD＋コーン41→回避あり3フレーム、交差する動きで手首30→3・肘0、前腕に重なる姿勢の動きはどれも0。尻尾どうしの交差はどの動きでも0。Δの最大は45度、1フレームの最大変化は回避ありで12.3度（交差する動き）。

- 体の回避をConeReaderで簡易化した版（`motion="*_compare"`、3列: D＋コーン／区間のclamp／ConeReaderの押し返し）: `tail_shared_avoid.buildConeDelta()`は、付け根と球の組ごとにConeReader（矢印＝打ち消し後の尻尾の向き、コーン＝付け根から球の中心、半角＝asin((r+余裕)/距離)、届かない距離では0へ）を置き、入った深さ（半角 − なす角）× 倍率を、(尻尾 × 球の方向)・upperarmのX軸 の符号で球と反対側へ回す量にし、深さが最大の組を Δ にします。肘・手首では胸や顔の前まで来るので全部の球を見ます（手首から胸の球を外すと、肘を深く曲げたときに胸へ食い込みました）。
- 結果（左、余裕1cm・倍率1.6）: 8cmより先の食い込みは、食い込みが多い姿勢の動きで手首 区間3／ConeReader 6・upperarm 0／1、交差する動きで手首 区間3／ConeReader 30（回避なしと同じ）。ConeReader版は球の側が入れ替わると反対側へ回り、1フレームで38〜57度の跳びが5回（区間の方式は0回）。計算用のノードは片腕で区間1,127、ConeReader 842（約25%減）。余裕2cm・倍率1.0では初期ポーズでも5.8度回りました。区間の方式を基準に残します。

- RBFで体の回避を作った版（`motion="*_rbf"`、4列: D＋コーン／区間のclamp／ConeReader／RBF）: `tail_shared_avoid.buildRbfDelta()`は、区間のclampの Δ を正解として UE RBF（`UERBFSolverNode`、位置のドライバー、ユークリッド距離、ガウス関数、半径0.25、重みの正規化）に学習させ、ポーズの重み × Δ を`blendWeighted`で足します。入力は鎖骨の空間で見た upperarm と lowerarm のX軸（単位ベクトル2つ）。肘を曲げて upperarm をひねると前腕ごと手首の付け根が回るので、肘の曲げの角度ではなく前腕の向きを入れます（肘の曲げの角度を入力にした版は、交差する動きでほとんど避けませんでした）。学習ポーズは rotateX −180〜135（45度刻み）× rotateY・rotateZ −120〜120（30度刻み）× 肘0・−45・−90・−130 のうち、入力が8度以内で重ならず腕が体に入らない1,204ポーズ。Maya標準の poseInterpolator も試しましたが、ツイストを無視すると入力が重なり、学習したポーズの上でも値を再現しなかったため使っていません。
- 結果（左右、8cmより先の食い込み）: 食い込みが多い姿勢の動きで手首 区間3／RBF 2、交差する動きで手首 区間3／RBF 6（右14）、前腕に重なる姿勢の動きはどれも0。RBFと区間のclampの Δ の差は平均1.8度（最大18.5度）、初期ポーズで0、跳びなし。右側の upperarm の尻尾の「深い食い込み」（7〜12フレーム、9〜13cm）は、胸のプロキシ（12角の円柱）の面が左右で対称でないために付け根の近くでかすっているもので、左右の尻尾は鏡像（ずれ0.0cm）です。
- 修正（2026-10-13）: 前腕のコーンの向きが右側だけ逆でした（右の骨は mirrorBehavior で X 軸が逆）。また、コーンの外でも aimConstraint で向けていたため、尻尾の向きが前腕の軸と平行になると向きが決まらず180度跳ぶことがありました。コーンの縁の向きへ向ける補助の関節を作り、案Dの回転と ConeReader の重み w で`pairBlend`（クォータニオン）するように直しました（`demo_tail_layers`も同じ）。これより前の前腕のコーンを含む動画は、右側にこの不具合があります。

#### 尻尾のレイヤー構造（効果ごとのON/OFF）と段階の並列表示

`demo_tail_layers.main()`は、1体の骨格の6本の尻尾を、効果ごとの関節を重ねたレイヤー構造で作ります。付け根の骨の子として elbowLayer（肘のスイング打ち消し、ry）→ twistLayer（ツイスト打ち消し、rx）→ avoidLayer（3本共通の体の回避 Δ、rx）→ restLayer（初期の向き −120、rx）→ tail（前腕のコーンの押し出し、`pairBlend`）の順に重ねます（打ち消しは X → Y の順に戻すので、外側が Y）。`tailLayers_CTRL`の`twistCancel`・`elbowCancel`・`forearmCone`・`bodyAvoid`（0〜1）で各効果を切り替え、`showStages`で同じ付け根から段階ごとの尻尾（灰＝素、水色＝＋ツイスト、緑＝＋肘、橙＝＋コーン）を細い線で並べて表示します。体の回避の Δ はツイストと肘の打ち消しがON（3本が平行）の前提です。

- 全部ONのとき、`demo_tail_twist_cancel`の「D＋コーン＋体の回避」と向きが一致し（差0.0度）、スイッチを段階の組み合わせにすると段階の尻尾と一致します（4段階とも差0.0度）。
- 録画は交差する動き→食い込みが多い姿勢の動き（720フレーム）を上面・正面・パースの3視点で撮ります。結果（左、付け根から8cmより先の食い込みフレーム／尻尾どうしの交差フレーム）: 素 8／0、＋ツイスト 156／95、＋肘 71／0、＋コーン 71／0、全部ON 6／0。

## 尻尾1軸回避のサンプルをHToolsから実行する

HToolsメニューの「rigging > tailAvoidanceSamples」を開くと、上の30のサンプル（入った側の接線保持・身体固定コーン・UE RBF・チェーンと3球・回転ベースのドライバー・簡易版2種・案1と案2・案1の実行時版・全身骨格での案1・腕上げとConeReaderの切り替え・尻尾6本のツイスト打ち消し（斜め後ろ／食い込む姿勢の上面・正面3列）・球が交わり始める跳び・跳びの対策・コーンでの近似・ConeReaderドライバー・方式比較）が一覧で出ます。

- **Build (play / scrub)**: 録画せずにシーンを作ります。タイムラインを再生・スクラブすると、HUDの式と数値がフレームごとに更新されます。スクラブで飛んだときは、前フレームとの差（step）を数え直します。
- **Record video**: 従来どおり録画し、数値検証して`.maya-output/verification/`へ保存します。FFmpegは`MAYA_VERIFICATION_FFMPEG`、PATH、ワークスペース内の`imageio_ffmpeg`の順に探します。

どちらもシーンを新規に作り直します。未保存の変更があれば確認が出ます。既存のHUDは削除せず、サンプルのウィンドウを開いている間だけ隠し、閉じると元の位置と表示に戻します。UE RBFのサンプルは、初回に`MayaUERBFPlugin`の信頼確認が出ます。サンプル本体は`tools/demo_joint_*.py`で、HToolsはそれを呼び出すだけです（ワークスペースの`tools/`が必要です）。

## iPadとSphinx

Claude Codeの完了報告にはDriveが返した閲覧URLを載せます。iPadではSafariまたはDriveアプリで開きます。アップロード直後はDriveの動画処理が終わるまで再生できない場合があります。

Sphinxへ掲載する場合は`drive-link.rst`のリンクを該当機能の説明へ追加します。公開Sphinxに載せたURLは誰でも見つけられます。毎回の検証URLを自動で公開Sphinxへ追記する処理はありません。

iPad実機での再生確認と、Claudeアプリ内の直接再生確認は別途必要です。
